= Near Caches
Near caches are local to Hot Rod clients and store recently used data so that every read operation does not need to traverse the network, which significantly increases performance.

Near caches:

* Are populated with read operations, calls to `get()` or `getVersioned()` methods. +
In the following example the `put()` call does not populate the near cache and only has the effect of invalidating the entry if it already exists:
+
[source,java,options="nowrap",subs="attributes+"]
----
cache.put("k1", "v1");
cache.get("k1");
----
+
* Register a client listener to invalidate entries when they are updated or removed in remote caches on {brandname} Server. +
If entries are requested after they are invalidated, clients must retrieve them from the remote caches again.
* Invalidate affected entries when listener connections are lost.

.Bounded near caches

You should always use bounded near caches by specifying the maximum number of entries they can contain.
When near caches reach the maximum number of entries, eviction automatically takes place to remove older entries.
This means you do not need to manually keep the cache size within the boundaries of the client JVM.

[IMPORTANT]
====
Do not use maximum idle expiration with near caches because near-cache reads do not propagate the last access time for entries.
====

.Bloom filters

Bloom filters optimize performance for write operations by reducing the total number of invalidation messages.

Bloom filters:

* Reside on {brandname} Server and keep track of the entries that the client has requested.
* Cannot be used with unbounded near caches.
* Are limited by the `max-bloom-filter-bits` attribute of the Hot Rod connector, which defaults to 64,000,000 bits.
  {brandname} Server rejects listener registrations that request a larger Bloom filter, so raise the limit if you use a larger `maxEntries`.

.Primary-owner near cache listeners

Hot Rod clients can use _primary-owner listeners_ to reduce network traffic and improve near-cache performance.
These listeners receive invalidations directly from the servers that own the entries, avoiding invalidation forwarding between cluster members.
When cluster membership changes, the client invalidates affected entries while retaining other cached entries.

The client automatically uses primary-owner listeners when you configure `HASH_DISTRIBUTION_AWARE` intelligence and the server cluster supports Hot Rod protocol 4.2 or later.
Bloom filter optimizations also apply to primary-owner listeners.

[NOTE]
====
Primary-owner listeners are managed by the client library exclusively for near caches.
You cannot register them directly using `@ClientListener` or `addClientListener()`.
No additional application code is required to use them.
====

.Fallback behavior

When primary-owner listeners are unsupported or cannot be established, the client automatically falls back to a cluster-wide listener.
This also allows near caches to work with older servers during rolling upgrades.
If a primary-owner listener becomes unavailable, the client retrieves affected entries remotely without caching them, while other entries can remain cached.

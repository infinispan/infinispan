= Near Caches
Near caches are local to Hot Rod clients and store recently used data so that every read operation does not need to traverse the network, which significantly increases performance.

Near caches:

* Are populated with read operations, calls to `get()` or `getVersioned()` methods. +
In the following example the `put()` call does not populate the near cache and only has the effect of invalidating the entry if it already exists:
+
[source,java,options="nowrap",subs="attributes+"]
----
cache.put("k1", "v1");
cache.get("k1");
----
+
* Register a client listener to invalidate entries when they are updated or removed in remote caches on {brandname} Server. +
If entries are requested after they are invalidated, clients must retrieve them from the remote caches again.
* Are cleared when clients fail over to different servers.

.Bounded near caches

You should always use bounded near caches by specifying the maximum number of entries they can contain.
When near caches reach the maximum number of entries, eviction automatically takes place to remove older entries.
This means you do not need to manually keep the cache size within the boundaries of the client JVM.

[IMPORTANT]
====
Do not use maximum idle expiration with near caches because near-cache reads do not propagate the last access time for entries.
====

.Bloom filters

Bloom filters optimize performance for write operations by reducing the total number of invalidation messages.

Bloom filters:

* Reside on {brandname} Server and keep track of the entries that the client has requested.
* Cannot be used with unbounded near caches.

.Primary mode

When a Hot Rod client uses `HASH_DISTRIBUTION_AWARE` intelligence and connects to a {brandname} Server cluster running Hot Rod protocol 4.2 or later, the client automatically operates in _primary mode_ for near caches.

[IMPORTANT]
====
Primary mode is an internal near-cache optimization managed entirely by the client library.
You cannot register a primary-owner listener directly using `@ClientListener` or `addClientListener()`.
No change to application code is required to benefit from primary mode.
====

In primary mode, the client registers a separate listener on each cluster member that is a primary owner of at least one cache segment.
Each server sends invalidation events only for keys it owns as the primary owner, so no inter-node forwarding is required.
The client reads cached entries directly from the primary-owner channel, which eliminates the latency of a round-trip to a non-primary node.

When the cluster topology changes — for example because a node joins or leaves — the server sends a `CACHE_TOPOLOGY_CHANGED_EVENT` (op `0x4A`) to each registered listener.
The client uses this event to update its consistent hash, invalidate entries whose primary owner changed, and install or remove per-node listeners accordingly, all without clearing the entire near cache.

Bloom filters work the same way in primary mode as in the standard cluster-listener mode.
Each primary-owner server maintains its own bloom filter for the keys that the client has cached from that server's segments.

.Fallback to cluster-wide listener

If the cluster or any individual server does not support Hot Rod protocol 4.2, or if the client cannot establish primary-owner listeners on enough servers, the client falls back automatically to the standard cluster-wide listener.
The fallback is logged at `WARN` level.
If the initial registration of primary-owner listeners fails, the client remains in fallback mode until it is restarted.

During a rolling upgrade the client switches modes dynamically.
When a server running an older protocol version joins the cluster, the client downgrades to the cluster-wide listener and clears the near cache.
Once all servers support Hot Rod protocol 4.2 again, the client upgrades back to primary-owner listeners and clears the near cache.

= Interceptor chain

The interceptor chain is the central processing pipeline in {brandname}.
Every cache operation, whether a simple `get` or a distributed `put`, flows through an ordered chain of interceptors.
Each interceptor handles a specific cross-cutting concern and delegates to the next interceptor in the chain.

== How the chain works

The chain holds its interceptors in an ordered list inside `AsyncInterceptorChainImpl`, where each interceptor keeps a reference to the next one and passes control along that link when invoked.
When a cache operation is invoked, execution starts at the first interceptor and proceeds through the rest of the chain.
Each interceptor can:

* Execute logic before passing control to the next interceptor
* Modify or inspect the command
* Short-circuit the chain by returning a result directly
* Execute logic after the next interceptor returns (post-processing)

All interceptors support asynchronous execution through `CompletionStage`, avoiding thread blocking during remote calls and I/O operations.

== Interceptor class hierarchy

All interceptors extend `BaseAsyncInterceptor`.
Most concrete interceptors extend `DDAsyncInterceptor`, which implements the Visitor pattern for type-safe command dispatch.

== Default chain order

The interceptor chain is assembled when a cache starts by `InterceptorChainFactory.buildInterceptorChain()`.
Interceptors are appended one after another, so their position in the chain matches that assembly order.
The table below shows a representative chain for a distributed synchronous cache with cross-site backups and an asynchronous persistent store configured (non-transactional).

[cols="1,3,4"]
|===
|Order |Interceptor |Responsibility

|1
|`VersionInterceptor`
|Manages entry versioning. Present only in non-transactional caches.

|2
|`IsMarshallableInterceptor`
|Verifies that keys and values can be marshalled before serialization happens. Present only when an asynchronous store is used.

|3
|`CacheMgmtInterceptor`
|Handles cache management commands such as clear or size requests. Always present in the chain.

|4
|`StateTransferInterceptor`
|Sets the topology id on each command and retries it if a topology change happens while processing. Present for clustered caches that use state transfer, plus transactional invalidation caches.

|5
|`*LockingInterceptor`
|Acquires and releases locks before delegating further down the chain. Non-transactional chains use `NonTransactionalLockingInterceptor`, while transactional caches use a pessimistic or optimistic variant.

|6
|`*BackupInterceptor`
|Replicates write commands to backup sites for cross-site replication, wrapping them in a `SingleXSiteRpcCommand`. Present when backups are configured.

|7
|`EntryWrappingInterceptor`, then persistence interceptors
|Wraps cache entries so that downstream interceptors see transactional state. Persistence loaders and writers (`ClusteredCacheLoaderInterceptor` and `DistCacheWriterInterceptor` in clustered modes) are inserted immediately after this interceptor, before any distribution handling.

|8
|`*DistributionInterceptor`
|Routes commands to the correct owners in distributed or replicated modes: `TriangleDistributionInterceptor` for distributed caches running in embedded mode, otherwise `NonTxDistributionInterceptor`. Invalidation mode uses `InvalidationInterceptor`, and local caches add no routing interceptor here.

|9
|`NonTxIracRemoteSiteInterceptor`
|Handles write commands received from backup sites and applies cross-site metadata and merge policies. Present on all clustered chains.

|10
|`SegmentHashInterceptor`
|Maintains per-segment hashes of entries so that conflicts can be detected when two partitions are merged back together. Present only when the cache resolves conflicts at merge time (a merge policy other than `NONE`) and no shared store is used.

|11
|`CallInterceptor`
|Executes the actual cache operation on the data container. Always last in the chain.
|===

Additional interceptors appear depending on configuration, inserted within this order:

* `BatchingInterceptor`: added first only when invocation batching is enabled (disabled by default). Handles manual batch demarcation.
* Transactional caches add a transaction trio after state transfer handling: `TransactionSynchronizerInterceptor` for clustered caches, then `TxInterceptor`, and finally the locking interceptor. When transaction notifications are enabled, `NotificationInterceptor` follows right after the locking interceptor so that locks are still held while it fires prepare/commit/rollback events to listeners.
* Caches with L1 enabled add `L1LastChanceInterceptor` before entry wrapping, plus either `L1TxInterceptor` or `L1NonTxInterceptor` after persistence handling.
* Caches with asynchronous cross-site backups add an IRAC local site interceptor (`NonTxIracLocalSiteInterceptor`, or the optimistic/pessimistic transactional variants) between L1 and distribution/invalidation routing.
* Clustered caches that do not allow reads and writes during a partition (a `whenSplit` value other than `ALLOW_READ_WRITES`) add `PartitionHandlingInterceptor`.
* Version-aware caches swap `EntryWrappingInterceptor` for `VersionedEntryWrappingInterceptor`, and synchronous distribution/replication modes use `VersionedDistributionInterceptor` instead of the regular routing interceptors.

Not all interceptors are present in every chain: local caches skip state transfer, backup, distribution, and cross-site handling entirely.

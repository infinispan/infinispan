== DefaultConsistentHashFactory

=== Pros

* **Tightest load balance** of all distributed-cache factories. Guarantees
  `floor(N×O/n) ≤ owned ≤ ceil(N×O/n)` for every node, for both primary and total ownership.
* **Minimal segment movement** on topology change. `updateMembers` retains all existing ownership
  assignments that are still valid; `rebalance` makes the smallest perturbations needed to restore
  balance rather than recomputing from scratch.
* **Full proportional capacity factor support** — every ownership decision compares
  `owned / capacityFactor` ratios directly, so a node with factor `2.0` receives exactly twice
  as many segments as a factor-`1.0` node, to within floor/ceil rounding.
* Accidental side effect: segments assigned to a node tend to be *contiguous ranges*, which gives
  slightly better cache locality when iterating owned data.

=== Cons

* **Non-deterministic across caches.** Two distributed caches with identical member lists can
  produce different consistent hashes if they were created at different times or experienced
  different topology histories. This breaks use cases that require cross-cache segment routing
  agreement (e.g., shared key spaces, HotRod smart routing for multiple caches).
* **Not topology-aware.** Backups may land on nodes sharing the same rack or site, reducing
  fault tolerance.
* The greedy iterative algorithm is **O(numNodes² × numSegments)** per pass, which can be slow
  for clusters with hundreds of nodes and thousands of segments.

---

== SyncConsistentHashFactory

=== Pros

* **Fully deterministic.** Any two caches with the same member list and capacity factors produce
  identical consistent hashes, regardless of topology history. This is essential for:
  ** HotRod smart routing — clients can compute the primary owner independently.
  ** Multiple caches sharing a key space needing consistent primary routing.
  ** Embedded caches that must agree on ownership without coordination.
* Uses **hash-distance based assignment** which inherently respects the ring structure, giving the
  assignment a natural geometric interpretation.
* The virtual-node approach (multiple hash positions per node) smooths distribution without
  requiring the sequential ordering of `DefaultConsistentHashFactory`.
* **Capacity factors supported** via geometric distance scaling — higher-capacity nodes appear
  closer to segments in the priority queue and receive proportionally more of them.

=== Cons

* **Excess segment movement on rebalance.** Because `rebalance` always recomputes from scratch via
  hashing, it ignores the existing assignment entirely. Segments that could stay in place are
  unnecessarily moved. In the worst case, a single node leaving can cause O(numSegments) segment
  moves even though O(numSegments / numNodes) moves are sufficient.
* **Slightly worse load balance** than `DefaultConsistentHashFactory` in edge cases, particularly
  when `numSegments` is small relative to `numNodes` or when capacity factors are highly skewed.
* **Capacity balance is "good" not "tight"** — the distance-scaling mechanism is an indirect
  proxy for capacity, not a direct ratio guarantee. Behaviour under highly skewed capacity factor
  distributions is harder to predict.
* The `fudgeExpectedSegments` tuning parameters are empirically derived, not analytically proven,
  which makes behaviour under unusual capacity factor distributions harder to predict.
* **Not topology-aware.**

== TopologyAwareConsistentHashFactory

=== Pros

* **Maximises backup fault tolerance** across failure domains. For a segment with `numOwners`
  owners, it attempts to place owners across distinct sites first, then distinct racks, then
  distinct machines, before settling for distinct nodes. This is the best choice when hardware
  failure domains are important.
* Gracefully **degrades** when topology information is incomplete — falls back to node-level
  diversity if site/rack/machine IDs are not configured.
* Inherits `DefaultConsistentHashFactory`'s **tight primary load balance**, **minimal primary
  movement**, and **full proportional capacity factor support** for the primary-owner phase.
* `TopologyInfo.getExpectedOwnedSegments()` distributes capacity correctly across topology levels
  — nodes in larger sites absorb proportionally more segments even when their individual capacity
  factors are equal.

=== Cons

* **Non-deterministic** across caches (inherits from `DefaultConsistentHashFactory`).
* **Primary owners are not topology-aware.** The primary-owner phase is purely load-balanced;
  topology diversity is only applied to backups. A site failure can leave segments with no
  surviving primary even when backups are on other sites.
* **Most expensive** factory. The multi-level add and replace passes (SITE → RACK → MACHINE →
  NODE, twice each) make this significantly more expensive than the base `DefaultConsistentHashFactory`
  for large clusters.
* Topology awareness only works if nodes are configured with `siteId`, `rackId`, and `machineId`
  in the JGroups transport configuration. Silently degrades without warning if not set.

---

== TopologyAwareSyncConsistentHashFactory

=== Pros

* **Both deterministic and topology-aware** — the only legacy factory with both properties.
  The best existing choice for multi-datacenter deployments that also require consistent client-side
  routing when `HistoryHintedRendezvousConsistentHashFactory` is not suitable.
* Topology constraints are enforced **inline** during hash-distance assignment via efficient
  integer lookup arrays, avoiding the costly post-assignment replacement passes of
  `TopologyAwareConsistentHashFactory`.
* Inherits all determinism guarantees of `SyncConsistentHashFactory`.
* **Most sophisticated capacity handling of any legacy factory** — `computeExpectedSegments`
  uses `TopologyInfo.getExpectedOwnedSegments()` combining capacity and topology level, so a
  node's target segment count reflects both its weight and its position in the cluster hierarchy.

=== Cons

* Inherits `SyncConsistentHashFactory`'s **excess segment movement** on topology changes.
* **Explicitly not recommended for low segment counts** (`numSegments < numNodes`). The combination
  of topology constraints with distance-based assignment produces poor load balance in this regime.
* **Capacity balance is "good" not "tight"** — inherits the geometric distance-scaling limitation
  from `SyncConsistentHashFactory`.
* Most complex implementation — combining distance scoring, topology lookup arrays, and
  multi-position constraints simultaneously.
* Primary owners are still **not topology-aware** (same limitation as `TopologyAwareConsistentHashFactory`).

---

== ReplicatedConsistentHashFactory

=== Pros

* **Simple and cheap.** Round-robin primary assignment is O(numSegments). Rebalance is O(numSegments
  × numNodes).
* Correct handling of `membersWithoutState` — new joiners do not become primaries until they have
  received all data.
* Appropriate and sufficient for replicated caches where every node owns every segment — only
  primary ownership matters.

=== Cons

* **Non-deterministic** across caches.
* **No topology awareness.**
* **Capacity factors do not affect distribution.** Fractional factors (e.g., `0.5`, `2.0`) are
  accepted without error but silently ignored — round-robin and rebalance treat all nodes as
  equal. Only zero-capacity exclusion via `membersWithoutState` is honoured.

---

== SyncReplicatedConsistentHashFactory

=== Pros

* **Deterministic** for replicated caches, matching the primary owner of `SyncConsistentHashFactory`
  for distributed caches with the same members. This allows mixed replicated/distributed topologies
  to route to the same primaries.
* Clean delegation — reuses all `SyncConsistentHashFactory` logic without duplication.

=== Cons

* Inherits `SyncConsistentHashFactory`'s **excess segment movement** on topology changes.
* **Stricter capacity factor validation** than `ReplicatedConsistentHashFactory` — any value
  other than `0.0` or `1.0` throws `IllegalArgumentException` at construction time. Fractional
  capacity is not silently ignored; it is actively rejected.
* Creates intermediate `DefaultConsistentHash` objects during conversion that are immediately
  discarded — minor but unnecessary GC pressure.

---

== HistoryHintedRendezvousConsistentHashFactory

NOTE: This is the *default factory* for `DIST_SYNC` caches, introduced in 16.3.

=== Pros

* **Deterministic** — rendezvous scores are a pure function of `(segment, node.uuid,
  capacityFactor)`. No history dependency.
* **Near-minimal segment movement** — the rendezvous base ensures that only segments involving
  the changed node are candidates for movement. The bounded-load greedy correction then minimises
  the actual moves within that candidate set.
* **History-hinted rebalancing** — when rebalancing, prior owners of a segment are preferred over
  cold candidates whenever they have capacity. This further reduces unnecessary data movement
  across topology changes without sacrificing load balance.
* **Stable-state idempotency** — when all segments already have the correct owner count and all
  members have segments, `rebalance()` skips Phases 1 and 2 entirely and runs only primary
  redistribution. Prevents `waitForNoRebalance` from looping unnecessarily.
* **Primary owner balance** is addressed by a primary-swap pass, matching
  `DefaultConsistentHashFactory`'s approach.
* **No virtual nodes** required — rendezvous hashing gives each segment an independent score per
  node, avoiding the virtual-node approximation used by `SyncConsistentHashFactory`.
* **Full proportional capacity factor support — inherent, not bolted on.** Dividing the hash
  score by `capacityFactor(n)` before ranking mathematically gives higher-capacity nodes
  proportionally more "slots" in the score space. The bounded-load correction tightens this to
  exact floor/ceil bounds.
* Produces `DefaultConsistentHash` — no new serialisation code needed.

=== Cons

* **Higher computation cost than Sync.** The greedy correction is O(numSegments × numNodes) —
  more expensive than `SyncConsistentHashFactory` but far cheaper than an MCF solver.
* **Segment contiguity is lost.** Like `SyncConsistentHashFactory`, rendezvous hashing scatters
  segments pseudo-randomly. The minor cache-locality benefit of contiguous segment blocks (an
  accidental property of `DefaultConsistentHashFactory`) is not preserved.
* **Requires all cluster members to be at or above 16.3.0** — falls back to
  `SyncConsistentHashFactory` during rolling upgrades until all nodes are upgraded.

== Choosing a Factory

[cols="2,3",options="header"]
|===
| Use Case | Recommended Factory

| Standard distributed cache, single or multi-node deployment
| `HistoryHintedRendezvousConsistentHashFactory` (default since 16.3)

| Multiple caches sharing a key space, or HotRod smart routing across caches
| `HistoryHintedRendezvousConsistentHashFactory` (deterministic by design)

| Replicated cache, standard deployment
| `ReplicatedConsistentHashFactory`

| Replicated cache with mixed replicated/distributed topology routing alignment
| `SyncReplicatedConsistentHashFactory`

| Legacy: non-deterministic, tight balance, minimal movement
| `DefaultConsistentHashFactory`

| Legacy: deterministic, slightly looser balance, excess movement
| `SyncConsistentHashFactory`
|===

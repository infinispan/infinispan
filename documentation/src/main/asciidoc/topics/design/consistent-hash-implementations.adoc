= Consistent Hash Factory Implementations
:toc: left
:toclevels: 3
:icons: font

This document describes each `ConsistentHashFactory` implementation in Infinispan, covering its algorithm,
design intent, configuration, and open questions. For a side-by-side comparison of pros and cons, see
xref:consistent-hash-comparison.adoc[Consistent Hash Comparison].

== Interface Contract

All factories implement
`org.infinispan.distribution.ch.impl.ConsistentHashFactory` and must satisfy:

* `create(numOwners, numSegments, members, capacityFactors)` — returns a *balanced* CH.
* `updateMembers(baseCH, newMembers, capacityFactors)` — removes leavers; does *not* add new owners
  beyond what is needed to ensure every segment has at least one owner. Returns `baseCH` unchanged
  if members and capacity factors are the same.
* `rebalance(baseCH)` — returns a balanced CH for the same member set.
* `union(ch1, ch2)` — returns a CH whose owner list for every segment is the union of both inputs,
  allowing a live topology switch from `union(ch1, ch2)` to `ch2` without state transfer.

A CH is *balanced* when `rebalance(ch).equals(ch)`.

== Capacity Factors

A *capacity factor* is a per-node floating-point weight that controls the relative number of
segments a node should own compared to other nodes. A node with capacity factor `2.0` should own
twice as many segments as a node with capacity factor `1.0`. A capacity factor of `0.0` means the
node is a member of the cluster view but should not own any data (e.g., a query-only node).

If no capacity factors are supplied (the map is `null`), all nodes are assumed to have a capacity
factor of `1.0`.

The table below summarises how each factory implements capacity factor support:

[cols="3,1,4",options="header"]
|===
| Factory | Support level | Mechanism

| `DefaultConsistentHashFactory`
| Full proportional
| Ownership decisions compare `owned / capacityFactor` ratios directly. Target =
  `numSegments × numOwners × capacityFactor(n) / totalCapacity`. Zero-capacity nodes excluded entirely.

| `SyncConsistentHashFactory`
| Good (geometric)
| Capacity converted to a distance multiplier: `distanceFactor = minCapacity / nodeCapacity`.
  Higher capacity → smaller distance → wins more segments in the priority queue.
  Target segments also scaled by capacity in `computeExpectedSegments`. Balance is good but
  not as provably tight as `Default`.

| `TopologyAwareConsistentHashFactory`
| Full proportional + topology-scaled
| Inherits `Default`'s direct ratio tracking. `TopologyInfo.getExpectedOwnedSegments()` further
  scales targets so that capacity is distributed correctly within and across topology levels.

| `TopologyAwareSyncConsistentHashFactory`
| Good (geometric + topology-scaled)
| Overrides `computeExpectedSegments` to use `TopologyInfo.getExpectedOwnedSegments()` (capacity
  and topology combined). Assignment still uses distance scaling from parent. Most sophisticated
  capacity handling of any existing factory, but balance is "good" not "tight".

| `ReplicatedConsistentHashFactory`
| Zero/one only (ignored for balance)
| Round-robin `create` ignores capacity entirely. Rebalance targets `numSegments / numMembers`
  with no capacity weighting. Capacity factors are stored and forwarded to the resulting CH
  but play no role in distribution. Zero-capacity nodes are excluded via `membersWithoutState`.

| `SyncReplicatedConsistentHashFactory`
| Zero/one only (enforced, throws on other values)
| `computeMembersWithoutState` throws `IllegalArgumentException` for any value other than `0.0`
  or `1.0`. Zero = excluded from primary ownership; one = normal member. No fractional support.

| `HistoryHintedRendezvousConsistentHashFactory`
| Full proportional (inherent)
| Dividing the hash score by `capacityFactor(n)` before ranking is mathematically equivalent to
  giving a node proportionally more "slots" in the score space. A node with factor `2.0` wins
  roughly twice as many segments in expectation with zero additional code. The bounded-load greedy
  correction in Step 3 then tightens this to exact `floor`/`ceil` bounds. Zero-capacity nodes
  score `+∞` and are excluded.
|===

== 1. DefaultConsistentHashFactory

`org.infinispan.distribution.ch.impl.DefaultConsistentHashFactory`

=== Intent

The original, production default for distributed caches. Produces the tightest possible load balance
with minimal segment movement on topology changes. Does *not* guarantee cross-cache determinism.

=== Algorithm

`create` and `rebalance` run a two-phase greedy builder:

. **Primary owner phase** — iterates segments sequentially. For each segment:
  .. Assigns the segment to the node with the worst primary-owned/capacity ratio.
  .. Swaps primary owners with existing backups when a backup has a better ratio.
  .. Performs replacement passes, first allowing up to `numOwners` total owners per segment, then
     `numOwners + 1`, to ensure every over-loaded primary can be displaced.

. **Backup owner phase** — iterates segments sequentially:
  .. Removes extra owners leftover from the primary phase.
  .. Adds backup owners greedily, always choosing the node with the lowest owned/capacity ratio.
  .. Replaces backup owners in segments where a non-owner has a better owned/capacity ratio.

`updateMembers` constructs a new builder from the base CH (retaining existing owner lists minus
leavers) and only runs a rebalance sub-pass for segments that lost all owners.

==== Balance Guarantee

----
floor(numOwners * numSegments / numNodes) <= owned(n) <= ceil(numOwners * numSegments / numNodes)
----

for every node `n` (both primary and total), provided all capacity factors are equal.
With capacity factors the bounds scale proportionally.

=== Capacity Factor Handling

Every ownership decision is made by comparing `owned / capacityFactor` ratios:

* `findNewPrimaryOwner` / `findNewBackupOwner` — both select the candidate whose
  `(owned ± 1) / capacityFactor` ratio is most favourable, ensuring all swaps converge toward
  proportional balance.
* Zero-capacity nodes are excluded from ownership entirely before the algorithm runs. They remain
  in the member list (so topology changes can be detected) but never appear in any segment's owner
  list.
* Capacity factors are stored verbatim in the resulting `DefaultConsistentHash` and forwarded
  through `updateMembers`, `rebalance`, and `union`.

=== Produces

`DefaultConsistentHash` — a flat array of per-segment owner lists.

=== Configuration

Used automatically for distributed caches unless overridden with
`HashConfigurationBuilder.consistentHashFactory(...)`.

=== Open Questions

* The greedy algorithm is O(numNodes² × numSegments) per pass. For clusters with thousands of nodes
  this becomes expensive — is there a threshold above which a faster approximation should be used?
* The sequential iteration over segments (0 → N) during assignment accidentally produces contiguous
  segment blocks per node. Is this property worth preserving explicitly, or is it acceptable to lose
  it in future implementations?
* Should primary-owner balance and total-owner balance be weighted differently when capacity factors
  are set?

== 2. SyncConsistentHashFactory

`org.infinispan.distribution.ch.impl.SyncConsistentHashFactory`

=== Intent

Guarantees that any two caches with the same member list produce the *same* consistent hash,
regardless of how those caches were created or their topology history. This is required when
multiple caches share a key space and must route to the same primary owner (e.g., embedded caches
used together, or HotRod client segment routing).

=== Algorithm

Uses hash-distance based assignment. Each node gets `numNodeHashes = 32 - leadingZeros(numSegments)`
virtual hash positions derived from `MurmurHash3(nodeUUID, virtualNodeIndex)`. Each segment has a
canonical hash position at the midpoint of its hash-space slot.

Assignment proceeds in two passes (primary owners, then all owners) via a priority-queue:

. For each segment, compute the *scaled distance* from the segment's hash position to each node's
  nearest virtual hash position, scaled by `minCapacity / nodeCapacity` to give higher-capacity
  nodes effectively closer distances.
. Build priority queues of `(segment, node, distance)` tuples sorted ascending by distance.
. Assign owners iteratively, each iteration allowing each node up to an increasing number of
  segments (`fudgeExpectedSegments`), until all segments have `numOwners` owners.

`rebalance` always calls `create` from scratch — there is no attempt to preserve the existing
assignment.

=== Capacity Factor Handling

Capacity factors are converted to *distance factors* before the assignment loop:

----
distanceFactor[n] = minCapacity / capacityFactor[n]
----

The raw hash distance between a segment and a node's virtual position is then multiplied by this
factor before entering the priority queue. Nodes with higher capacity receive a smaller
`distanceFactor`, which makes their virtual positions appear geometrically closer to every
segment — so they naturally win more segments in the priority queue.

`computeExpectedSegments` also scales the per-iteration target for each node by
`capacityFactor(n) / totalCapacity`, so the load-balancing correction step accounts for capacity
proportionally.

Zero-capacity nodes are sorted to the end of the member list (after `sortMembersByCapacity`) and
excluded from the assignment entirely. Their `distanceFactor` would be infinite, so they could
never win a segment anyway.

*Important caveat:* balance is "good" rather than provably tight. Because capacity is encoded
indirectly as a geometric distance multiplier rather than a direct ratio, the balance guarantee is
a strong empirical property rather than the exact floor/ceil bound provided by
`DefaultConsistentHashFactory`.

=== Produces

`DefaultConsistentHash`.

=== Determinism Property

For a fixed member list and capacity factor map, `create`, `rebalance`, and `updateMembers` (when
called on a CH built from those members) all produce identical output on any JVM because:

* Node hash positions are derived solely from `UUID` bits, which are stable across JVMs.
* Segment hash positions are derived solely from `numSegments`.
* The priority-queue algorithm is deterministic given those inputs.

=== Known Limitation

Segment movement on topology change is higher than `DefaultConsistentHashFactory`. Because
`rebalance` recomputes from scratch, segments that were stable under the old topology may be
reassigned to different nodes even when the mathematical optimum would leave them in place.

Example from the class Javadoc:
----
Before D leaves: {0:AB, 1:BA, 2:CD, 3:DA}
Sync result:     {0:BC, 1:CA, 2:CB, 3:AB}
Optimal result:  {0:AB, 1:BA, 2:CB, 3:AC}
----

=== Open Questions

* The number of virtual hash positions per node (`numNodeHashes`) is logarithmic in `numSegments`.
  Is this sufficient for good distribution at very large segment counts (e.g., 4096+)?
* The `fudgeExpectedSegments` step function is empirically tuned. Is there a closed-form derivation
  for optimal step sizes given arbitrary capacity factor distributions?
* When two nodes have identical UUIDs (impossible in practice but possible in tests), the algorithm
  produces undefined results. Should this be explicitly detected and rejected?

== 3. TopologyAwareConsistentHashFactory

`org.infinispan.distribution.ch.impl.TopologyAwareConsistentHashFactory`

=== Intent

Extends `DefaultConsistentHashFactory` to maximise backup-owner diversity across failure domains
(site → rack → machine → node). For a segment with `numOwners` owners, the factory attempts to
place each owner in a distinct site first, then distinct rack, then distinct machine, before
falling back to node-level diversity.

=== Algorithm

Inherits the full primary-owner phase from `DefaultConsistentHashFactory` unchanged (primary owners
are load-balanced only, not topology-diversified).

Overrides the backup-owner phase with a three-level iterative replacement strategy using
`TopologyInfo`:

. **Add phase (per level: SITE, RACK, MACHINE, NODE)** — for each segment that still has fewer
  than `numOwners` owners, add candidates that do not duplicate an already-represented location at
  this level. Repeats with relaxed load limits until all segments are filled.

. **Replace phase (per level: SITE, RACK, MACHINE)** — for each segment where distinct locations at
  this level is below the maximum possible, replace a duplicate-location backup with a node from
  an unrepresented location.

. **No-level replace phase** — replaces overloaded backups with underloaded nodes, subject to the
  constraint that diversity at all levels is maintained or improved.

=== Topology Levels

Topology information comes from `Address.getSiteId()`, `Address.getRackId()`, and
`Address.getMachineId()`. If a node does not set these values, all nodes appear to be in a single
site/rack/machine and the factory degrades to `DefaultConsistentHashFactory` behaviour.

=== Capacity Factor Handling

Inherits `DefaultConsistentHashFactory`'s direct ratio-based tracking unchanged for both the
primary-owner and backup-owner phases.

Additionally, `TopologyInfo.getExpectedOwnedSegments(node)` is used as the per-node target in the
add and replace passes. This method accounts for capacity *and* topology level simultaneously: a
node in a large site is expected to hold proportionally more segments than a same-capacity node in
a small site, because the site must collectively absorb its fair share of the total ownership.

Zero-capacity nodes are excluded via the standard `checkCapacityFactors` validation inherited from
`AbstractConsistentHashFactory`.

=== Produces

`DefaultConsistentHash`.

=== Known Limitations

* Primary owners are not topology-aware — a site failure can make all primaries for a segment
  unavailable even when backups are on surviving sites.
* Non-deterministic across caches with the same members (inherits from `DefaultConsistentHashFactory`).
* Most expensive factory to run due to the multi-level iterative replacement passes.

=== Open Questions

* Should primary owner placement also consider topology diversity, even at the cost of some primary
  load imbalance?
* When `numOwners > numSites`, what is the correct priority: maximise site diversity first, or
  maximise load balance first?
* The replace passes iterate owners in reverse order (highest backup position first) for stability.
  Is this ordering provably optimal or just empirically stable?

== 4. TopologyAwareSyncConsistentHashFactory

`org.infinispan.distribution.ch.impl.TopologyAwareSyncConsistentHashFactory`

=== Intent

Combines the cross-cache determinism of `SyncConsistentHashFactory` with the topology-aware
placement of `TopologyAwareConsistentHashFactory`. Intended for multi-datacenter deployments where
HotRod clients must compute the correct primary owner independently and backup owners must span
failure domains.

=== Algorithm

Extends `SyncConsistentHashFactory`. Overrides two methods:

* `createBuilder` — returns a specialised `Builder` that pre-computes integer lookup arrays
  (`siteLookup`, `rackLookup`, `machineLookup`) mapping each sorted node index to its topology
  integer ID.

* `nodeCanOwnSegment(segment, ownerPosition, nodeIndex)` — adds topology constraints inline
  during the hash-distance priority-queue assignment:
  ** Owner position 0: no constraint (any node).
  ** Positions 1 .. numSites-1: candidate must be in a distinct site from all earlier owners.
  ** Positions numSites .. numRacks-1: candidate must be in a distinct rack.
  ** Positions numRacks .. numMachines-1: candidate must be in a distinct machine.
  ** Remaining positions: candidate must be a distinct node.

* `computeExpectedSegments` — uses `TopologyInfo.getExpectedOwnedSegments()` for per-node targets,
  which accounts for the topology-level capacity distribution, rather than the flat capacity-factor
  formula used in the base class.

=== Produces

`DefaultConsistentHash`.

=== Determinism Property

Fully deterministic for a given member list, inheriting from `SyncConsistentHashFactory`.

=== Known Limitation

Explicitly documented: **not recommended when `numSegments < numNodes`**. The topology constraints
combine with the distance-based assignment to produce poor load balance when there are too few
segments to spread across both nodes and topology levels simultaneously.

=== Capacity Factor Handling

Overrides `computeExpectedSegments` to use `TopologyInfo.getExpectedOwnedSegments(node)` instead
of the flat capacity formula used in `SyncConsistentHashFactory`. This gives the most
sophisticated capacity handling of any existing factory: capacity is distributed correctly both
within each topology level and across levels.

The distance-factor mechanism from `SyncConsistentHashFactory` is inherited unchanged for the
actual assignment loop. The override only affects how many segments each node is *expected* to
receive; the priority-queue ordering still uses geometric distance scaling.

Zero-capacity nodes are excluded via `sortMembersByCapacity` inherited from the parent builder.

=== Open Questions

* The owner-position thresholds (0 → sites → racks → machines → nodes) are hardcoded. Should they
  be configurable to support deployments with only rack-level diversity, skipping site-level
  constraints?
* When topology information is partially configured (some nodes have site IDs, others do not), the
  behaviour is undefined. Should missing topology IDs be treated as a distinct synthetic value or
  as a match-all wildcard?
* How does the excess-segment-movement problem (inherited from `SyncConsistentHashFactory`) interact
  with topology constraints? Could a node lose topology diversity on a rebalance that the base
  class would have left stable?

== 5. ReplicatedConsistentHashFactory

`org.infinispan.distribution.ch.impl.ReplicatedConsistentHashFactory`

=== Intent

Factory for replicated caches where every node owns every segment as a backup. Only *primary*
ownership is significant — it determines which node handles writes and coordinates replication.

=== Algorithm

`create` — assigns primary owners via round-robin over the member list, skipping members in the
`membersWithoutState` list (new joiners or zero-capacity nodes).

`updateMembers` — retains existing primary assignments where possible. For segments whose primary
left the cluster, assigns the least-loaded surviving node. If `rebalance` is requested, additionally
runs a pass that moves segments from most-loaded to least-loaded nodes until all nodes hold
`floor(numSegments / numNodes)` primaries.

`membersWithoutState` is computed as nodes that either have `capacityFactor == 0` or that are new
members not present in the previous CH.

=== Capacity Factor Handling

Capacity factors are *stored* in the resulting `ReplicatedConsistentHash` and forwarded through
all operations, but they do **not** affect primary ownership distribution:

* `create` uses a plain round-robin, completely ignoring capacity factors for assignment.
* The rebalance pass targets `floor(numSegments / numMembers)` (integer division, no capacity
  weighting) — all surviving members are treated as equal regardless of their capacity factors.
* `findLeastUsedNode` / `findMostUsedNode` count segments only, not capacity-weighted segments.

The only effective use of capacity factors for replicated caches is **zero-capacity exclusion**:
nodes with `capacityFactor == 0` are placed in `membersWithoutState` and will never be assigned
as primary owners.

Fractional capacity factors (e.g., `0.5` or `2.0`) are accepted without error but have no effect
on distribution. This is a known gap — see open questions.

=== Produces

`ReplicatedConsistentHash` — stores only the list of primary owner indices, not full per-segment
owner lists, since all nodes own all segments.

=== Known Limitations

* Non-deterministic across caches with the same members.
* No topology awareness.
* The rebalance pass (`findLeastUsedNode` / `findMostUsedNode`) is O(nodes) per segment move,
  which is acceptable but not cache-efficient for large clusters.

=== Open Questions

* Should `ReplicatedConsistentHashFactory` support topology-aware primary placement (e.g., prefer
  primaries in a specific site)?
* The `capacityFactor` validation in `computeMembersWithoutState` throws on any value other than
  `0.0` or `1.0`. Is this restriction intentional and documented to users?

== 6. SyncReplicatedConsistentHashFactory

`org.infinispan.distribution.ch.impl.SyncReplicatedConsistentHashFactory`

=== Intent

Provides the same cross-cache determinism guarantee as `SyncConsistentHashFactory` but for replicated
caches. Ensures the primary owner of a segment in a replicated cache is the same node as the
primary owner of that segment in a distributed cache using `SyncConsistentHashFactory`, allowing
mixed-mode topologies to route reads consistently.

=== Algorithm

Delegates entirely to `SyncConsistentHashFactory` with `numOwners = 1`:

. Creates a `DefaultConsistentHash` via `SyncConsistentHashFactory.create(1, ...)`.
. Extracts the primary owner index for each segment.
. Wraps in a `ReplicatedConsistentHash`.

`updateMembers` and `rebalance` follow the same delegation pattern via `defaultFromReplicated` ↔
`replicatedFromDefault` conversion helpers.

=== Produces

`ReplicatedConsistentHash`.

=== Determinism Property

Fully deterministic for a given member list. Primary owner for segment `s` in a replicated cache
with members `M` will always be the same as the primary owner for segment `s` in a distributed
cache using `SyncConsistentHashFactory` with the same members `M`.

=== Capacity Factor Handling

`computeMembersWithoutState` (shared with `ReplicatedConsistentHashFactory`) **enforces** that
capacity factors for replicated caches are either `0.0` or `1.0`, throwing
`IllegalArgumentException` for any other value:

[source,java]
----
if (capacityFactor != 0f && capacityFactor != 1f) {
    throw new IllegalArgumentException(
        "Invalid replicated cache capacity factor for node " + a);
}
----

* `0.0` — node is placed in `membersWithoutState` and excluded from primary ownership.
* `1.0` — normal member, eligible for primary ownership.
* Any other value — hard rejection at construction time.

This means `SyncReplicatedConsistentHashFactory` is stricter than `ReplicatedConsistentHashFactory`
(which accepts but ignores fractional values).

=== Known Limitations

* Inherits `SyncConsistentHashFactory`'s excess segment movement on topology change.
* The `defaultFromReplicated` conversion creates intermediate `DefaultConsistentHash` objects that
  are immediately discarded, adding minor GC pressure on large clusters.

=== Open Questions

* When a replicated and distributed cache share members, the primary-alignment guarantee is exact.
  When they diverge (different member lists), is there a defined behaviour or is it simply
  best-effort?

== 7. HistoryHintedRendezvousConsistentHashFactory

`org.infinispan.distribution.ch.impl.HistoryHintedRendezvousConsistentHashFactory`

=== Status

*Implemented and tested.* Default factory for `DIST_SYNC` caches since 16.3.

=== Intent

Combines the cross-cache determinism of `SyncConsistentHashFactory` with near-minimal segment
movement by using rendezvous (highest-random-weight) hashing as the base assignment, a
bounded-load greedy correction for floor/ceil ownership balance, and a history-hinted rebalance
pass that minimises unnecessary data movement across topology changes.

=== Core Idea

Uses *rendezvous hashing* as the base assignment for `create()` and as the starting point for
`rebalance()`. When rebalancing, prior owners of a segment are preferred over cold candidates
whenever they have capacity — the segment data is already warm there and reassigning it back
incurs no net movement cost.

=== Capacity Factor Handling

Capacity proportionality is an **inherent property** of the rendezvous scoring formula:

----
score(s, n) = murmurHash3(s, n.uuid) / capacityFactor(n)
----

A node with factor `2.0` ranks first for approximately twice as many segments. The bounded-load
greedy correction in `SegmentOwnershipBalancer` tightens this to exact `floor`/`ceil` bounds.
Zero-capacity nodes are excluded before ranking.

=== Algorithm

==== `create()` / `build()` — two-phase assignment

* **Phase 1**: for each segment, assign the top `actualNumOwners` nodes by rendezvous score.
* **Phase 2**: `SegmentOwnershipBalancer.apply()` — drains over-ceil nodes and redistributes
  primary ownership via free position swaps to achieve tight floor/ceil balance.

==== `rebalance()` — three-phase history-hinted algorithm

* **Stable-state shortcut**: if all segments have exactly `actualNumOwners` owners AND all
  non-zero-capacity members own ≥1 segment, skip Phases 1+2 and run only primary redistribution
  over the existing owner sets. Returns `baseCH` unchanged if nothing changed.
* **Phase 1**: pure rendezvous initial assignment (same as `build()` Phase 1).
* **Phase 2 — history hints**: for each overloaded node, scan its backup segments. For each,
  check whether any prior owner (from `baseCH`) is currently under-loaded. If so, prefer that
  prior owner — data already warm, no net movement cost.
* **Phase 3**: `SegmentOwnershipBalancer.apply()` — handles remaining excess and primary
  redistribution.

=== Segment Movement Properties

* **Node leaves**: only segments previously owned by the leaving node are in play.
* **Node joins**: the new node claims segments it ranks highest on; history hints ensure prior
  owners are preserved where they have capacity.
* **Stable topology**: `rebalance(create_result)` is idempotent when all members have segments.

=== Produces

`DefaultConsistentHash` (reuses existing data structure unchanged).

=== Determinism Property

`create()` is fully deterministic. `rebalance()` is deterministic given the same `baseCH` input.

=== Rolling Upgrade

Requires all cluster members at or above `NodeVersion.SIXTEEN_THREE` (16.3.0). Falls back to
`SyncConsistentHashFactory` during rolling upgrades via the version guard in
`ClusterCacheStatus.effectiveConsistentHashFactory()`.

=== Future Considerations

* **Dynamic capacity factor recalculation**: capacity factors are currently set at configuration
  time. Runtime updates would require configuration/topology layer changes; the CH factory itself
  is already capable of handling updated factors via `rebalance(ch)`.
  _Deferred: CH factory capable; requires configuration/topology layer work._

* **Dynamic segment count**: changing `numSegments` on a live cache requires solving routing
  consistency, state-transfer, and persistence concerns that are independent of the CH factory.
  _Deferred: significant cross-cutting design work required._

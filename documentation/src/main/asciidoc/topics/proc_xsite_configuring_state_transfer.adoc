= Configuring cross-site state transfer
Change cross-site state transfer settings to optimize performance and specify whether operations happen manually or automatically.

.Procedure

. Open your {brandname} configuration for editing.
. Configure state transfer operations as appropriate.
.. Specify the number of entries to include in each state transfer operation with `chunk-size` or `chunkSize`.
.. Specify the time to wait, in milliseconds, for state transfer operations to complete with `timeout`.
.. Set the maximum number of attempts for {brandname} to retry failed state transfers with `max-retries` or `maxRetries`.
.. Specify the time to wait, in milliseconds, between retry attempts with `wait-time` or `waitTime`.
.. Specify if state transfer operations happen automatically or manually with `mode`.
+
[IMPORTANT]
====
Automatic state transfer between cluster only available for asynchronous backup strategy.
====
. Save and close your {brandname} configuration for editing.

[NOTE]
====
For synchronous backups, `timeout` applies to each attempt to send a state transfer chunk.
After an attempt fails, {brandname} waits for `wait-time` before retrying, and each retry gets a new timeout period.
You can set `wait-time` equal to or greater than `timeout`.
For example, `timeout="1000"` and `wait-time="2000"` allow each attempt one second to complete, with a two-second delay before the next retry.
Both values must be greater than zero.
====

For synchronous backups, the backup replication timeout must be strictly less than a positive locking `acquire-timeout`.
{brandname} rejects equal or greater backup timeouts, including when you update either timeout at runtime through the administration API.
Concurrent writes might time out waiting for locks held during cross-site replication.
This requirement concerns the backup `timeout` attribute, which is separate from the state transfer `timeout` attribute.
